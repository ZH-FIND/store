# CoffeeFlow V1 PRD：线上下单 + 商品管理

> 状态：评审中（待业务方确认）
> 基线：CoffeeFlow V0（门店订单看板，12 条种子订单，前后端已可运行）
> 约束：2 小时练习项目，优先"能跑通、能验收"，明确做减法

## 1. 背景与目标

V0 只有门店侧的单据视图：店员能看订单列表、看详情、把订单从"待制作"推到"已完成"。所有订单都是后台灌进去的。

V1 要让**顾客自己下单**，并让**门店能控制卖什么**。

一句话目标：顾客能查到卖什么、下单拿到取餐码、凭码查进度、制作前自己取消；门店能停售/恢复商品，且原 V0 看板照常工作。

## 2. 范围

### 2.1 本版要做（Must）

| 编号 | 能力 | 角色 |
|------|------|------|
| F1 | 浏览商品：名称、图片、价格、可售状态 | 顾客 |
| F2 | 选择取餐门店 | 顾客 |
| F3 | 一个订单选多个商品及各自数量 | 顾客 |
| F4 | 提交订单，返回订单金额与取餐码 | 顾客 |
| F5 | 用取餐码查询订单详情与最新状态 | 顾客 |
| F6 | 门店开始制作前取消订单 | 顾客 |
| F7 | 停售 / 恢复商品 | 门店 |
| F8 | V0 门店订单看板继续正常使用 | 门店 |

### 2.2 本版不做（Out of Scope）

- 支付、退款、优惠券、会员
- 账号 / 登录 / 鉴权体系
- 门店维护界面（门店为只读种子数据）
- 库存扣减、制作产能、排队算法
- 订单金额的并发对账、审计流水

## 3. 关键决策（本轮已确认）

| # | 决策 | 选择 | 影响 |
|---|------|------|------|
| D1 | 数据模型 | **规范化拆表**：`orders` 只留订单头，商品明细进 `order_items` | V0 看板改读聚合，接口契约不变 |
| D2 | 取餐码 | **独立短码**，全局唯一递增（4 位数字，从 1001 起） | 不复用订单号；不重置、不需冲突重试 |
| D3 | 顾客身份 | **手机号后四位**，下单时填写 | 取消订单校验：取餐码 + 手机号后四位 |
| D4 | 价格模型 | **商品统一价，规格（小/中/大杯）不加价** | `size` 仅作展示，不进金额计算 |
| D5 | 顾客端界面 | **单页 Tab 切换**（门店看板 / 顾客点单），不引入 vue-router | 复用现有 SPA 与样式 |
| D6 | 停售粒度 | **全局商品级**（`product.available`）⚠️ 简化项 | 停售影响所有门店，与用户故事五措辞有出入，见 §8 |

## 4. 数据模型

### 4.1 现状问题（必须解决）

V0 的 `orders` 一张表同时装"订单"和"订单里的商品"：

```
orders(product_code, drink_name, size, quantity, items)
                                          ▲         ▲
                        "商品条目数"，非杯数      管道符拼的商品名，无数量/单价
```

- 一个订单多商品时，只记名字，**没有每个商品的数量和单价**，无法算金额。
- `quantity` 在 12 条种子数据里恒等于 `items` 的条目数，**不是 V1 要的"每商品杯数"**。

### 4.2 目标模型

```
   stores ──┐
            ├──► orders ──► order_items ──► products
   products ┘        ▲                          ▲
   （只读种子）      │                          └── 价格 / 可售状态
              pickup_code, total_amount,
              phone_last4, status
```

**`products`（新增）**

| 字段 | 说明 |
|------|------|
| product_code | 主键，`CF-BEV-001` ~ `CF-BEV-014`（与现有 14 张商品图 1:1） |
| name | 商品名，如"燕麦拿铁" |
| price | 统一价（D4：规格不加价） |
| available | 可售状态（D6：全局级） |

**`stores`（新增，只读）**

| 字段 | 说明 |
|------|------|
| store_id | 主键 |
| store_name | 国贸店 / 望京店 / 中关村店 / 三里屯店 / 朝阳大悦城店（沿用 V0 现有门店） |

**`orders`（改造，只留订单头）**

| 字段 | 变化 |
|------|------|
| id | 不变，`CF-xxxx` 订单号 |
| store_name | 保留 |
| customer_name | 保留 |
| phone_last4 | **新增**（D3） |
| pickup_code | **新增**（D2） |
| total_amount | **新增**，下单时按明细汇总的**快照** |
| status | 不变，5 态 |
| created_at / estimated_ready_at / note | 保留 |
| ~~product_code / drink_name / size / quantity / items~~ | **移除**，改为由 `order_items` 聚合得出 |

**`order_items`（新增）**

| 字段 | 说明 |
|------|------|
| order_id | 外键 → orders.id |
| product_code | 外键 → products.product_code |
| drink_name | 下单时**快照** |
| size | 下单时**快照** |
| quantity | **该商品杯数**（V1 新语义，与 V0 的订单级 quantity 不同源） |
| unit_price | 下单时**快照**的单价 |
| subtotal | quantity × unit_price |

### 4.3 V0 兼容映射（关键）

V0 的 3 个接口响应字段**必须一个字都不变**。拆表后按以下规则聚合：

| V0 响应字段 | V1 取值方式 |
|-------------|-------------|
| `items` | `order_items` 中该单所有 `drink_name` 的列表（按插入顺序） |
| `quantity` | `COUNT(order_items)` —— **保持"条目数"语义**，不是杯数 |
| `productCode` / `drinkName` / `size` | 取该单**第一条**明细（把"主商品"定义明确下来） |

> 这样 V0 的测试基线天然成立，例如 CF-1003 有 3 条明细 → `quantity=3`、`items=[抹茶拿铁,美式,冷萃]`。

### 4.4 种子数据迁移

12 条历史订单需拆成订单头 + 明细：

- 历史单**没有每商品杯数**，迁移时统一按 **每个商品 1 杯** 拆（等价于 V0 的"条目数"语义）。
- 明细的 `product_code` 按 `drink_name` 反查 `products`；`size` 取原订单的 `size`。
- `unit_price` 取 `products.price`；`total_amount` 按明细汇总。
- 历史单的 `pickup_code` / `phone_last4` 用占位值（历史单不参与顾客侧查询）。

## 5. 状态机与业务规则

```
            ┌──────────── 顾客可取消（仅此一处）────────────┐
            │                                              ▼
   NEW ─────┴──► IN_PROGRESS ──► READY ──► COMPLETED   CANCELLED
  待制作          制作中          待取餐      已完成
   ▲
   └── 顾客下单后落在此态
```

| 规则 | 说明 |
|------|------|
| R1 下单初始态 | 新订单进入 `NEW`（= 待制作） |
| R2 取消窗口 | **只有 `NEW` 可被顾客取消**；`IN_PROGRESS` 及之后拒绝 |
| R3 取消校验 | 必须同时匹配 `pickup_code` 与 `phone_last4`，否则拒绝 |
| R4 取消结果 | 状态置 `CANCELLED`，**不删单**（看板仍可见） |
| R5 停售拦截 | `available = false` 的商品**不允许下单**，下单接口整体拒绝并指明商品 |
| R6 金额快照 | `total_amount` 与 `unit_price` 在**下单时刻**固定，后续改价不影响已有订单 |
| R7 状态推进 | 沿用 V0：店员在看板上按 `NEW→IN_PROGRESS→READY→COMPLETED` 单向推进 |

## 6. API 契约

### 6.1 V0 接口（保持不变，回归红线）

```
GET   /api/health
GET   /api/v1/orders?status=
GET   /api/v1/orders/{orderId}
PATCH /api/v1/orders/{orderId}/status
```

> `PATCH` 语义沿用 V0「无约束直接改状态」（含 `CANCELLED`）。顾客取消走下面的专用接口，以便做身份校验。

### 6.2 V1 新增接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/products` | 商品列表（名称/图片码/价格/可售状态） |
| GET | `/api/v1/stores` | 门店列表 |
| POST | `/api/v1/orders` | 顾客下单，返回 `orderId` + `pickupCode` + `totalAmount` |
| GET | `/api/v1/orders/pickup/{pickupCode}` | 按取餐码查订单详情与状态 |
| POST | `/api/v1/orders/{orderId}/cancel` | 顾客取消，请求体含 `phoneLast4` |
| PATCH | `/api/v1/products/{productCode}/availability` | 停售 / 恢复商品 |

**下单请求（示意）**

```json
{
  "storeId": "S001",
  "customerName": "顾客13",
  "phoneLast4": "8888",
  "items": [
    { "productCode": "CF-BEV-001", "size": "大杯", "quantity": 2 }
  ],
  "note": "少冰"
}
```

**下单响应（示意）**

```json
{
  "orderId": "CF-1013",
  "pickupCode": "1001",
  "totalAmount": 56.00,
  "status": "NEW"
}
```

## 7. 用户故事与验收标准

### US1 顾客浏览商品
作为顾客，我希望查看当前商品、价格和可售状态。

- [ ] 打开顾客点单页，能看到 14 个商品，每个显示名称、图片、价格
- [ ] 被停售的商品可见但**标记为不可售、不可选**

### US2 顾客提交订单
作为顾客，我希望选择取餐门店、选一个或多个商品及数量并提交。

- [ ] 能选门店、能对同一商品加减数量、能选多个不同商品
- [ ] 下单成功后展示**订单金额**与**取餐码**
- [ ] 下单后门店看板能立刻看到这条新订单，状态为"待制作"

### US3 顾客查询进度
作为已下单顾客，我希望通过取餐码查订单详情和最新状态。

- [ ] 输入取餐码能查到订单，展示商品明细、金额、当前状态
- [ ] 店员在看板推进状态后，顾客侧再查能看到新状态

### US4 顾客取消订单
作为已下单顾客，我希望在门店开始制作前取消订单。

- [ ] 订单为"待制作"时，凭取餐码 + 手机号后四位可取消成功
- [ ] 订单已"制作中"及之后，取消被拒绝并给出明确提示
- [ ] 手机号后四位不匹配时取消被拒绝

### US5 门店管理商品状态
作为门店店员，我希望临时停售或恢复商品。

- [ ] 能把某商品置为停售，顾客侧立即变为不可选
- [ ] 能恢复为可售，顾客侧立即可选
- [ ] 停售的商品**无法被下单**（即使前端被绕过）

### US6（回归）V0 看板继续可用
- [ ] 12 条历史订单仍全部可见，筛选/详情/推进状态均正常
- [ ] V0 的 3 个接口响应结构与字段名**零变化**
- [ ] 后端既有测试全部通过

## 8. 非功能与约束

| 项 | 要求 |
|---|---|
| 部署 | 沿用 `docker compose up --build`，三条容器（mysql / backend / frontend）不变 |
| 数据库变更 | 新增 DDL 落在 `sql/` 下，与现有 `00` / `01` 脚本同一套初始化流程 |
| 测试 | 后端 `mvn verify`、前端 `npm run check && npm run lint && npm test && npm run build` 必须通过 |
| 并发 | 取餐码全局唯一由数据库自增保证；本版不处理下单并发竞争 |

## 9. 待确认项（需业务方拍板）

1. **停售粒度**：当前按全局商品级实现（D6），而用户故事五措辞是"门店店员停售"。若验收要求门店级隔离，需新增 `store_product` 关系表 + 种子数据，属额外交付。
2. **取餐码是否长期复用**：当前全局递增不复用。真实业务通常每日重置。
3. **历史订单的取餐码/手机号占位值**：历史单不参与顾客侧查询，是否需要清理可见性。
4. **14 个商品的定价**：PRD 未指定价格档位，需要业务方给出价目表（本版可自拟占位价）。
